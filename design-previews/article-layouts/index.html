Agent 工程实践

从一次请求，看懂 Agent 的执行过程

沿着请求进入、模型决策、工具调用和结果回传，梳理一个可观测的 Agent Runtime 应该如何工作。

先划清执行边界一次请求的生命周期工具调用与恢复观察系统发生了什么实践清单

一个 Agent 看起来像是在不断“思考”，但落到工程实现，它是一组可以追踪的状态变化。真正需要设计的，是这些变化发生时，系统如何保存上下文、执行工具，并把结果交还给用户。

这篇文章从一次普通请求出发：用户要求修改一个函数，并运行测试。我们沿着执行顺序，观察每一层负责什么，以及失败后应该从哪里恢复。

先划清执行边界

会话管理、推理循环和工具执行承担不同职责。把它们放在同一个函数里，最初写起来很快；当你需要取消任务、恢复对话或定位异常时，边界就会变得重要。

一个实用的判断：某一轮失败之后，你能否仅通过事件记录，解释它停在了哪里？
  • 会话层保存输入与历史，为下一轮提供连续上下文。
  • 运行时推进模型与工具之间的循环，管理执行状态。
  • 工具层完成有明确输入、输出和失败语义的操作。

一次请求的生命周期

接收到请求，并不等于任务已经完成。运行时要明确区分“已接受”和“已结束”，让界面和服务使用同一套状态语义。

事件不仅服务于界面展示，也构成排查问题的依据。尤其是持续时间较长的任务，流式连接关闭可能由多种原因触发，不能直接作为完成信号。

工具调用与恢复

工具调用应该有稳定的标识，并让成功、失败和取消都变成可处理的结果。下面是一个简化的事件接口：

runtime-events.ts · 示例
type RunEvent =
  | { type: "started"; runId: string }
  | { type: "tool_result"; callId: string; output: unknown }
  | { type: "completed"; output: string }
  | { type: "failed"; reason: string };

// 由终态事件确认执行结果，而不是连接状态。

如果工具会修改外部数据，恢复执行还需要考虑重复调用。相比无条件重试，先识别副作用，再决定是否重跑，通常能减少难以解释的行为。

观察系统发生了什么

记录日志之前，先明确你需要回答哪些问题。执行耗时、失败位置和最终结果，比大量没有关联信息的文本更有用。

观察对象保留的信息帮助回答
单轮执行runId、开始时间、终态这一轮是否已经完成？
模型调用耗时、输出类型、错误时间消耗在哪里？
工具调用callId、工具名、执行结果哪个操作失败了？

实践清单

先实现一条完整、可观察的执行路径，再逐步增加并行工具、记忆和恢复机制。一个规模很小但终态明确的系统，比难以解释的大型循环更适合作为起点。

  • 区分请求已接受与任务已完成。
  • 为每一次工具调用保留独立标识。
  • 让失败与取消成为显式的结果。
  • 用一次失败实验检查事件记录是否足够。
